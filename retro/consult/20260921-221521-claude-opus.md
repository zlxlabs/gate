# 二、第一性原理四步

## 1. 这东西为什么存在？没有它会怎样？

**存在的理由**：`@v2` 是个会移动的标签，「移动 v2」就是发布动作（`AGENTS.md:19`）。移动标签这件事必须有人做，而且必须满足三个约束：只指向 canary 真跑绿过的 commit（否则移动标签 = 给全舰队无验证推送）、只能前进（否则回滚会静默降级下游）、不能破坏 caller 契约（`tests/test_gate_caller_contract_guard.py`）。

**没有它会怎样**：退回到逐仓钉 SHA。注意——`README.md:161` 提到 gate-hub 已经有 `scripts/bump_caller_pins.py`，而且它「固定先同步白名单再改 caller」。**所以「20 个仓手工改 pin」这个恐吓其实站不住**，bump 工具已经存在。真正失去的是「零接触升级」和「一次改动立刻全舰队生效」。

**顺带一个必须说的文档漂移**：`README.md:58` 写「目前只有 gate-hub 接入」，`templates/caller-gate-v2.yml:89` 还是 `@__PINNED_GATE_SHA__` 加一大段「canary 期间必须钉死 commit SHA，不用移动引用」的论证（`:83-88`），而同一文件 `:109-110` 又提到「v2 moving tag advances」，`AGENTS.md:19` 则说「调用方钉 `@v2`」。**同一个仓里三份文档对「下游到底钉什么」说法不一致。** 我无法从本仓核实舰队规模，这是未验证项——但在一个「发布物就是 SHA」的仓里，这种漂移本身是事故因子。

## 3. 能不能让问题根本不出现？

分三个层次，诚实地说清哪个是真消灭、哪个只是消灭了失败。

### 层次 A：真正消灭「目标落后于 tip」这个**状态**

唯一办法：**让 main 上每个 commit 在落地时就是 canary-verified 的**——合并队列（merge queue），候选合并结果先过 canary 再进 main。那样 tip 恒等于 verified，「落后」这个状态不存在。

**为什么现在做不了**：`templates/caller-gate-v2.yml:16-28` 明确写了这个决定——`merge_group` 故意没接，因为 `gate-v2.yml` 里每个表达式都假设 `github.event.pull_request` 存在，真来一个 merge_group 事件会在聚合器的 argparse 上硬失败。重开这个决定 = 改 `gate-v2.yml` 的表达式 + 聚合器 CLI 契约，personal 档不值。

还有一个陷阱值得说破：即使你「PR head sha 过了 canary 再合并」，**merge commit 的 SHA 不等于 PR head sha**，而 `AGENTS.md:19-22` 强制 merge commit。所以「合并前验证」在不上 merge queue 的前提下**天然无法覆盖真正会被发布的那个 SHA**。这不是疏忽，是数学。

**结论**：真消灭这个状态在架构上可达，但被一个显式的、有理由的更早决定挡住。我不推荐现在动它。

### 层次 B：消灭「被拒绝的 push」这个**事件**（推荐）

状态消灭不了，但**在不可推的状态下发起推送**这个动作可以彻底消灭：把「可推性」变成选取阶段的前置条件，而不是 push 阶段的事后失败。

这不是降噪，是把一个不该发生的操作从代码路径上删掉。区别很重要：
- 「两态化：把已知失败标黄」= 处理问题（你的方向 3 当前写法）
- 「不可推的目标根本不进入候选集」= 消灭问题

### 层次 C：消灭「等待期无限延长」（触发问题）

即使 B 做了，v2 仍要等到 tip 被验证。等待本身正确，**等待没有结束信号**才是缺陷。正确的结束信号是「canary 验完了 tip」这个事件本身。
